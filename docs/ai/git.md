# Git workspace

## Git workspace

- `docs/design/git-pr-interface.md`, `docs/design/git-issues-interface.md`, and `docs/design/git-inbox-interface.md` specify the completed `[1] Diffs` / `[2] PR` / `[3] Issues` / `[4] Inbox` workspace inspired by gh-dash. Preserve Diffs as the offline local Git workspace; keep PR, Issues, and Inbox responsibilities in separate models/services/UI and retain fake `gh`/fixture coverage for every remote read or write. Review the relevant documents before changing navigation, capabilities, safety, limits or persistence, and update their evidence when behavior changes.
- Remote PR, Issue, and Inbox lists automatically request the next page when selection reaches the final loaded row and render the loading state inside the list. PR and Issues refresh the visible section and selected details every 30 seconds while active; reopening a stale tab refreshes promptly, and `[R]` refreshes both list and details. Their configured refresh interval still reloads every configured section and reconstructs the same page depth reached in the current session. Background refresh must preserve the visible data on failure and must not race a page request. A superseded list/detail read cancellation is not a user-facing error; explicit PR/Issue refresh can replace a pending page only when the retired page cannot publish afterward, while timed and foreground refreshes wait for pagination.
- Keep long-lived Git caches bounded: local project contexts and PR/Issue section results retain at most 64 entries per cache, while PR/Issue detail caches retain at most 32. Cache hits must refresh LRU recency, and disposing the owning session clears its entries.
- PR/Issue detail readers must verify the exact active request after awaiting I/O before publishing or caching a response/page. Cancelled and disposed readers cannot repopulate caches or release replacement controllers. A cache hit cancels the previous pending selection, and PR detail keys include `updatedAt` as well as the head SHA so discussion changes invalidate old snapshots.
- PR and Issue detail hooks share the narrowly scoped `useGitRemoteDetails` lifecycle. Initial debounce, explicit refresh and pagination have one request owner; repeated page actions in the same event batch dispatch once. Switching/deactivating a selection resets page-busy state, refresh supersedes an old page, and retained callbacks from another selection cannot start a new read. Keep per-tool data models, pagination/merge rules and sessions separate.
- Git resource registries snapshot and clear the retiring generation before invoking callbacks. Catch each synchronous/asynchronous failure independently and await all callbacks that return promises; one broken disposer must not skip its siblings or erase registrations belonging to a later generation.
- Each CI watch owns its cancellation controller. Stopping/unmounting aborts its reader, and late responses or queued timer callbacks must validate the exact live watch before notifying, updating state or scheduling again. Retire terminal watches before invoking notification callbacks so notification failure cannot repeat a completed watch.
- The PR Checks workflow reader scopes results and errors to the exact active selection generation, including head/summary changes and demo/deactivation transitions. Hide previous runs during render, before effect cleanup, and ignore both successes and failures after cancellation; never offer a previous PR's eligible runs while the next selection loads.
- PR/Issue/Inbox list rows memoize their formatted text by immutable summary, width, column selection, language and the Inbox saved marker where applicable. Selection, focus, palette changes, pagination loader frames and new outer arrays must not repeat date/Unicode/text formatting for unchanged rows. Keep colors and mouse callbacks live; do not freeze whole rows around mutable theme globals or add an unbounded cache outside mounted rows.
- Git remote status marks use palette-aware green for open, purple for merged, muted gray for draft or unknown, and red for closed. Keep PR/Issue state glyphs and Inbox's filled/unfilled unread mark, with a text state label in Inbox. Notification pages contain no subject state: resolve PR/Issue states through bounded, cancellable, repository-pinned background reads, cache only validated results for a short period, and leave unavailable or non-PR/Issue subjects neutral without blocking the list.
- Automated noninteractive `gh` calls reject already-aborted requests before spawning and settle timeout/cancellation only after their exact child closes; helpers that ignore `SIGTERM` must not remain running. Handle stdin pipe errors without exposing request content. Incomplete input with an otherwise successful exit is not confirmation: PR/Issue writes remain uncertain and are never replayed automatically. This transport is separate from the user's guided login/install PTY.
- On Bun 1.3.14, send automated `gh` stdin as bounded sequential byte chunks, require every `write(chunk, callback)` to succeed, and call `end()` only after the final callback before accepting exit zero. One large `write` and `end(payload)` can report completion while dropping a pipe error; do not rely only on `finish` or `writableFinished`. Keep real-child regressions for refused/partially read input, complete Unicode delivery, EOF and cancellation under backpressure on the pinned runtime.
- PR and Issue scope summaries show the exact `owner/repository` when only one remote repository is selected; use a numeric repository count only for multi-repository selections. Inbox refresh is always automatic and should show refresh copy only while an update is actually in progress.
- PR and Issue query editors share GitHub qualifier autocomplete. `[Ctrl+N/P]` moves through contextual suggestions and `[Ctrl+Y]` applies one; profile repositories appear as `repo:` completions. Keep the query itself authoritative and continue applying the structured account/repository scope separately.
- Query autocomplete walks candidates lazily and stops at its visible limit. Skip repository candidates when the active prefix cannot match `repo:`; do not allocate and filter an entire account catalog on every keystroke. Preserve repository-first order, existing-token exclusion and limit semantics.
- PR/Issue query normalization and qualifier recognition share the pure `model/search-query.ts` tokenizer. Preserve quoted whitespace and escaped quotes; words such as `repo:` or `author:@me` inside a literal phrase cannot supply scope or replace mandatory type/archive filters. Qualifiers with quoted values remain distinct from fully quoted text. Editing may retain an unfinished quote, but applying/saving must show the error inside the editor without losing draft or focus. Building a request also rejects it before appended filters could become part of that literal. Verify the resulting stdin queries with a fake `gh`, not only helper return values. This tokenizer is not a Boolean-expression parser.
- PR, Issues, and Inbox share guided GitHub CLI requirement and authentication panels. They explain `gh`, show the fixed detected install/update command or the host-pinned `gh auth login` command, and provide `[C]` copy plus a mouse/`[Enter]`-focusable mini terminal. Tuiminal starts only the user's login shell: it must never inject or execute the displayed command, capture/persist PTY input, or read a token. Forward both user input and terminal-emulator protocol responses to the active PTY; a stale exit callback must never detach a replacement shell, and `[Enter]` reopens a shell that exited. Poll for `gh >= 2.40.0` or a valid host login and reload the Git view automatically when ready; unmount stops only the owned shell process group.
- New GitHub profiles use English selector titles. PR starts with `My PRs`, `Review requested`, `All`, `Open`, and `Closed`; Issues starts with `My Issues`, `All`, `Open`, and `Closed`. `All` means every non-archived item in the configured repository/account scope, while `Open` and `Closed` apply the corresponding GitHub state. When loading configuration, migrate only exact untouched previous default sets; never replace selectors the user customized.
- PR and Issue persisted configurations share pure value normalization in `model/remote-config.ts`; keep their default section sets, allowed columns, repository validators, and PR-only preferences in the owning model. Shared parsing must preserve exact untouched-default migration and customized selector options.
- PR and Issue selector sections share pure ID generation, column/option validation, ordering, movement, and removal in `model/remote-sections.ts`; keep query normalization, section creation/update, and tool-specific types in their owning models.
- PR and Issue query/section editors share `ui/shared/GitRemoteSectionEditor.tsx`; their wrappers supply per-tool columns and parser while the shared view owns the identical focus stack, query autocomplete, fields, and action footer. Preserve the existing PR/Issue element IDs and keyboard scopes.
- PR and Issue sessions share only pure page aggregation and identity-based merging in `services/remote-session-items.ts`; retain their separate request controllers, auth generations, cache ownership, pagination, refresh timing, and disposal.
- PR and Issue dashboard hooks share the narrowly scoped `ui/shared/useGitRemoteDashboard.ts` lifecycle for load, refresh, pagination, generation checks, and notifications. Their wrappers supply the distinct sessions, demo flags, and notification sources; do not merge session data models or write workflows into that hook.
- All four PR/Issue list and detail caches use `services/remote-cache.ts` for bounded LRU insertion and hit recency; the owning sessions still set their 64/32 limits and clear caches on disposal.
- Inbox uses the authenticated host from the project PR profile but remains a separate REST-backed session and UI. Its default sections are Inbox, review requested, assigned, mentioned, and locally saved. Mark-read is explicit; done and unsubscribe require confirmation. Persist only saved thread IDs in `~/.config/tuiminal/git-inbox.json`, atomically with mode `0600`.
- PR and Issue searches require no initial setup. Without an explicit project profile, a launch inside a Git repository with a parseable GitHub `origin` defaults both tools to that repository; a launch outside Git, or without a parseable GitHub remote, defaults to the complete authenticated account scope. A broad account query is scoped with `user:<viewer>`, `org:<membership>`, and external `repo:<owner/name>` qualifiers so it never becomes an accidental GitHub-wide search. An explicitly saved empty repository list means `TODOS`/account scope.
- Issue searches use the same account-scope rule, always add `is:issue` and `archived:false`, and reject `is:pr`. The dense two-line list and Overview/Activity preview support configurable sections, columns, sort and limits; wide, medium and narrow terminals use side-by-side, stacked and one-pane layouts respectively.
- Issue writes cover comment, assign/unassign, label deltas, `gh issue develop --checkout`, close and reopen. Keep the prepare/re-authenticate/re-read/execute-once/reconcile flow; pin host, node ID, repository, number, state, `updatedAt` and auth generation. Timeout/cancellation after dispatch remains uncertain with no retry. Label and assignee edits must use complete details rather than search summaries, and checkout must pass the existing clone/remote/clean-worktree checks.
- Classify GitHub CLI connection failures, including TCP resets and HTTP 5xx, separately from confirmed command rejections. A failed Issue preflight sends no write; a connection failure after an Issue or PR write is uncertain and must never trigger an automatic retry. Issue writes may use one read-only reconciliation after a connection error to confirm the effect. Show concise localized connection guidance for failed list/detail refreshes while retaining usable data.
- PR and Issue creation is available from each remote tab with `[Ctrl+N]` and a mouse control, including empty lists. Forms keep drafts in memory and use `[Ctrl+S]` for one explicit create request. Choose the concrete repository through the shared searchable authenticated repository catalog picker; cancel its read on close, ignore late results, and keep a valid current selection available while it loads or fails. PR creation offers searchable, paged remote branch pickers labeled base and compare, clears both choices when the repository changes, and never pushes or checks out local Git. Read the selected repository's `default_branch` to suggest the PR base; never infer it from a selected PR. Cancel stale reads, preserve a manually chosen base, and keep the picker available if the suggestion fails. The compare choice maps to GitHub's `head` field. Suggest the PR title from the compare branch's latest remote commit subject; cancel stale reads and never overwrite a manually edited title. A failed suggestion must not block manual entry or creation. Recheck the authenticated viewer, repository identity and PR branches before dispatch. Only a response URL matching the host, repository, type and number confirms creation. Any post-dispatch failure is uncertain; preserve the draft and require the user to check GitHub before manually enabling another attempt.
- PR and Issue discussions expose exactly five reactions in this order: `[1]` 👍, `[2]` ❤️, `[3]` 🎉, `[4]` 😄, and `[5]` 👀. `[Shift+E]` reacts to the selected PR/Issue; in Activity, `[J/K]` selects comments, `[E]` reacts, and `[Enter]` replies. Keep the controls mouse-accessible and show them only for the selected comment; label the action `[E] Nova reação` whenever that comment already has a reaction. GitHub issue comments are flat, so a reply is a new comment prefixed with the selected comment's validated URL and an `@author` mention; parse that prefix on read, hide it from the body, and render the reply directly below its parent with visible nesting. Refresh the selected details after successful discussion writes. Reactions must re-read and validate the exact node type, ID, and URL before writing, execute once through GraphQL, then reconcile `viewerHasReacted`; replies retain the common direct-read uncertain-result protection.
- Git configuration is contextual: only the Git screen exposes it through global `[,]` settings. Its unified modal owns the local Diffs target, PR selectors, Issue selectors, one remote repository scope saved to both profiles, and the Git-wide browser choice. The repository tab lists `TODOS` plus every accessible owned, organization, and direct-collaborator repository. `[5] Browser` (compact `[5] Web`) saves the system browser, Browsh, Carbonyl, or terminal-browser in `~/.config/tuiminal/git-browser.json` with atomic `0600` writes; it applies to PR, Issue, Inbox, and workflow URLs. Browsh/Carbonyl run in an owned PTY modal and terminal-browser opens a separate pane. Validate HTTPS host and use argv, not a shell. `[Ctrl+P]` in Diffs opens that modal directly on the local target, where the user may choose an existing local Git repository and one of its local branches. Persist the selected Diffs repository separately in `~/.config/tuiminal/git-diffs.json`; changing it or checking out its branch must not alter or refresh the remote PR/Issue/Inbox scope. Do not restore the retired local PR/Issues configuration shortcuts; `[/]` remains the quick editor for the active query.
- Git configuration publishes local-project discovery and the remote repository catalog independently, including each loading/error state. Each load owns an abort controller: close/unmount/reload cancels the remote read, ignores old results, and cannot start a catalog request after cancelled version detection. An already-running local filesystem discovery may finish, but its retired result cannot update the modal. Keep read cancellation separate from explicit local project/branch writes.
- A local project/branch picker acquires a synchronous selection guard before dispatch; repeated activation in the same event batch must not repeat the operation. Closing or unmounting retires its UI callbacks, so late success/failure cannot close or update a replacement picker. This does not cancel or undo an already-dispatched Git operation. Handle backdrop clicks on the hit-tested overlay itself and ignore bubbled clicks from dialog children; a decorative lower layer cannot reliably receive them.
- Issue configuration lives in `~/.config/tuiminal/git-issues.yaml`, atomically written with mode `0600` and scoped by canonical project root. An empty repository list means account scope. Diffs, PR, Issues, and Inbox preserve independent state; shutting down Git must dispose all remote resource groups.
- Git Diffs behaves like a compact lazygit-style workspace for the selected local repository. It initially uses the repository from which Tuiminal was launched, but may switch independently to another repository and branch available on the machine.
- The local `[Ctrl+P]` configuration shortcut respects the focused Git keyboard scope and partial-stage panes. It must not steal autocomplete navigation from the command input, escape an open modal, handle an already-consumed event, or treat extra modifiers/key repeats as a new activation.
- The first Git tab visibly pairs `[1]` with `[C] Git · Diffs`; `[C]` toggles the same tab to `Git · Compare`. Compare reuses the selected local project and accepts local plus already-known remote refs. Once all selectors are applied, wide layouts place project, base, arrow, and compared cards in one row; narrower layouts stack all three. The result has a folder-grouped file tree and renders only the selected file, with `[Tab]`, `[H/L]`, and `[←/→]` switching tree/diff focus and a fixed shortcut footer that must remain visible above scrollable content. In every focused Git diff, `[Shift+H/L]` and `[Shift+←/→]` scroll the unwrapped code horizontally without changing pane focus; vertical scrolling must preserve that horizontal position, and the content width must include the complete longest rendered line. It uses the PR-style `base...compared` range, never checks out either ref, excludes uncommitted worktree changes, and returns to Diffs with `[C]` or `[Esc]`.
- The changed-file tree is grouped into real folders and distinguishes staged and unstaged changes. A directory chain with no files or sibling directories shows every folder name on its own line at the same indentation, while remaining one focusable/navigable block; its files sit one indentation level below the whole chain. File rows show only Git's two-character status code, with semantic colors per character; do not add redundant circle/question markers. Folder disclosure and names use colors distinct from files. Staging must update the visual snapshot optimistically, serialize repeated stage/unstage requests without disabling those actions, then reconcile only the Git status without losing useful selection context. Status-only reconciliation updates the mounted diff silently without a loading overlay or scroll reset; commit history loads after the usable worktree and is refreshed only when refs change. `[Space]` toggles the selected file or every descendant of the selected folder as one group; if any descendant is unstaged, it stages the whole folder, otherwise it unstages the whole folder. `[A]` on a folder always stages every descendant; on a file it retains the all-files toggle.
- Treat filenames from Git status as literal paths in single-file and folder diff, stage, unstage, and discard commands, including the unborn-HEAD fallback. `--` separates options but still permits Git pathspec wildcards and magic; use `--literal-pathspecs` before the subcommand so selecting one file or folder never includes matching neighbors. `[D]` opens an exact-target confirmation before restoring tracked files and removing new files, and folder discard cascades only through its descendants.
- `[Enter]` on a file-tree file opens and focuses its diff. A focused tracked text diff opens partial staging with `[S]`. This mode always uses the unified layout and presents the desired outside/inside-index state side by side, including already-staged hunks so they can be removed. `[S]` toggles hunk/line granularity without clearing pending transfers, `[H/L]` or horizontal arrows moves between the two lists, `[J/K]` or vertical arrows navigates, and `[Space]` transfers the current target. While partial staging is open, hide the Git command console and give its space to the two lists; focus is contained in them, boundary directions stay on their nearest list, `[Tab]` toggles only between them, and terminal focus shortcuts do not escape. Scroll the selected renderable itself into view rather than deriving an offset from its target index, because hunks occupy variable row counts; the last target must remain wholly above the action footer. `[Enter]` and `[Esc]` both apply the displayed state and exit. Give the active hunk one blue left rail spanning its complete scope. Hunk and line granularity must both keep line bodies rendered as code with syntax highlighting; granularity changes selection only. Re-read and compare both exact literal-path staged and worktree patches before applying selected directions through `git apply --cached` on stdin; stale sources must fail safely. Do not offer partial staging for untracked, deleted, binary, or mode-only changes.
- In Diffs, `[Tab]` cycles file tree, preview, and the Git command console below the preview. `[H/L]` and `[←/→]` move between the tree and preview, and `[T]` focuses the console. The console reserves seven visible output rows in both layouts; while its input is focused, `[F10]` toggles a maximized overlay across the complete preview panel, and the same action remains mouse-accessible in its header. It always renders a fixed `git` prefix, invokes the Git executable directly without composing a shell command, preserves stdout/stderr line structure instead of summarizing it, retains at most 2,000 lines, records commands caused by UI actions, and accepts explicit manual Git arguments. Manual input autocompletes commands, common options, local and already-known remote branches, tags, remotes, and changed paths; `[Ctrl+N/P]` navigates, `[Ctrl+Y]` applies, and `[Esc]` dismisses suggestions before leaving the input. Repository candidates come from local Git refs and must never fetch from the network merely to complete text. Its output scrolls with `[↑/↓]` while the input is focused and with the mouse. The focused framed panel uses the Git accent border. The file tree, Log, and full Git graph use `[J/K]` and `[↑/↓]` only while their own panel is focused; do not use `[N/P]` for local history. `[O]` opens Log, and `[V]` visibly identifies and cycles the diff layout. Keep the fixed shortcut footer mounted above scrollable content even during refreshes, actions, messages, and errors.
- A small commit graph remains visible under the file tree; fullscreen graph mode replaces the code/diff area. Graph rows show short hash and author initials. Size and bottom-align the mini graph from the rendered file-panel bounds, including its current compact focus rail, rather than estimating from the terminal dimensions; keep its horizontal inset symmetric in both framed and compact layouts when focus changes.
- Commit lanes need distinct, stable colors and clean Unicode connectors similar to lazygit. Do not render every branch/lane in the same color.
- Diff modes include unified, side-by-side, and intraline. Intraline mode represents a modified line once and highlights only the changed characters, rather than always showing separate full `-` and `+` lines. Its code cell must shrink beside the line-number gutter; never give both the gutter and code a combined width wider than the pane.
- Diff parsers distinguish file headers from content by hunk context: code beginning with `++` or `--` remains an added/removed line, including in partial staging and viewport height counts. Compute intraline character ranges only when that document's intraline rows are requested, reuse them for that immutable document, and release the temporary source-line array afterward; unified/split views must not pay for every file's character comparison.
- Git diff scrolling moves native code buffers, never the whole document or the split container. Keep line numbers, signs and change backgrounds fixed, both split columns visible and synchronized, and mouse-accessible `[Shift+H/←]` / `[Shift+L/→]` controls on a reserved bottom-right row. Leaving the diff or changing document/layout resets horizontal position; vertical movement retains it. Size native code cells from their rendered pane minus its fixed gutter (including after resize): percentage/flex sizing can hide the final character. Cover actual rendered suffixes, Unicode/tabs, colors, split bounds and focus reset, not only reported scroll offsets.
- Diffs show old/new line numbers, syntax highlighting, hunk context, additions/removals, and should remain visually stable without highlight flicker. Preserve the mounted diff while the next selected file loads, and do not feed preview-loading animation frames into the repository/branch header.
- The Diffs repository/branch header must not flex-shrink when preview content grows. Its row remains reserved during repeated file-tree navigation; test the actual painted header line across short/long diff changes in both layouts, not only component identity or reported height.
- `[O]` commit history uses expanded `git log`-style blocks with the colored topology lanes continuing through every line. Show the abbreviated hash and branch/tag decorations, merge parents when present, author plus email, relative date, changed-file count, `+/-` statistics, subject and a bounded commit body. Size and window the list by each block's real rendered height so the selected commit cannot disappear below the footer. Preserve selected-block contrast, grapheme-aware truncation, inert sanitized commit text, and direct opening of the selected commit diff. Keyboard and mouse navigation must work in files, commits, graph, and diff views.
